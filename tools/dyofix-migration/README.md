# מיגרציית היסטוריה לדיופיקס — runbook

ייבוא 7.5 שנות היסטוריה מ-iShop (133,194 הזמנות · 360,230 שורות · 75,186 לקוחות)
לתוך התקנת ה-WooCommerce של דיופיקס.

## ⚠️ סייל איקס

סייל איקס יושב על שרת אחר ו**אסור לגעת בו**. הסקריפט אוכף את זה בעצמו:
כל פקודת כתיבה (`customers`, `orders`, `relink`) קוראת קודם ל-`assert_dyofix_target()`,
שבודקת `home`, `siteurl`, `DB_NAME` ו-`ABSPATH`:

- מוצא `salex` באחד מהם → **עוצר**.
- לא מצליח לאמת `dyofix` באף אחד מהם → **עוצר**.

נבדק על 8 תרחישים (סייל איקס לפי URL / DB / webroot בנפרד, אותיות גדולות-קטנות,
התקנה זרה, קונפיג ריק) — כולם נחסמים; דיופיקס בדומיין ובטאנל עוברים.

## סדר הרצה

הכל מהתקנת דיופיקס בלבד:

```bash
cd /var/www/dyofix/public_html

# 1. מה באמת יש בקבצים (שמות המפתחות של ה-importer לא תועדו)
wp --require=dyofix-import.php dyofix inspect \
   --orders=~/dyofix-migration/orders.jsonl \
   --customers=~/dyofix-migration/customers.csv --allow-root

# 2. פרסור מלא בלי כתיבה + פענוח פערי הסכומים
wp --require=dyofix-import.php dyofix dry-run \
   --orders=~/dyofix-migration/orders.jsonl --allow-root

# 3. סמפל קטן, לאימות עין לפני הריצה המלאה
wp --require=dyofix-import.php dyofix customers --customers=... --limit=200 --allow-root
wp --require=dyofix-import.php dyofix orders    --orders=...    --limit=500 --allow-root

# 4. ריצה מלאה (הרץ ב-screen/tmux)
wp --require=dyofix-import.php dyofix customers --customers=... --allow-root
wp --require=dyofix-import.php dyofix orders    --orders=...    --allow-root

# 5. אחרי שהקטלוג ייטען — חיבור שורות ההזמנה למוצרים
wp --require=dyofix-import.php dyofix relink --dry-run --allow-root
wp --require=dyofix-import.php dyofix relink --allow-root
```

**חשוב:** להריץ את `inspect` ראשון ולעדכן את `Dyafix_Field_Map` בראש הקובץ אם שמות
המפתחות שונים ממה שהונח. הסקריפט נופל עם הודעה ברורה במקום לייבא זבל.

## תכונות שחשובות בריצה

- **חסין להפסקה** — כל הזמנה נושאת `_dyofix_src_order`; ריצה חוזרת מדלגת על מה שכבר נכנס.
  אפשר לעצור באמצע ולהריץ שוב את אותה פקודה.
- **`--limit`** על כל פקודה, לבדיקות.
- **סכום ההזמנה מהמקור הוא הקובע** — הסקריפט לא מריץ `calculate_totals()`. הזמנה שבה
  Σ השורות לא מסתדר עם הסכום מסומנת ב-`_dyofix_total_delta` ונשארת ניתנת לביקורת.
- **SKU נשמר על כל שורה** (`_dyofix_src_sku`) גם כשאין מוצר תואם — זו הסיבה שאפשר
  לייבא היסטוריה לפני הקטלוג ולשלם על זה מעט מאוד.
- **שקט** — מיילים, שינויי מלאי ואינדוקס ES מנוטרלים לאורך הייבוא. אף לקוח לא מקבל
  מייל על הזמנה מ-2019.
- **בלי סיסמאות** — סיסמאות iShop לא ניתנות למיגרציה; חשבון נוצר בלי סיסמה והכניסה
  הראשונה עוברת דרך איפוס.
- **הזמנות אורח** — 6,062 הזמנות בלי מייל נכנסות כהזמנות אורח (שם+טלפון), staff-visible,
  בלי חשבון, לפי ההחלטה בתוכנית.

## פער הסכומים — 15.49%

`report.txt` מדווח על **20,634 הזמנות (15.49%)** עם פער >1 ₪ בין Σ השורות לסכום המקורי.

ההשערה המובילה: ה-header במקור כולל **הנחת הזמנה** (עמודה 4) ו**ריבית הזמנה** (עמודה 6)
ברמת ההזמנה, אבל מסווג השורות מטפל רק בשורות ההנחה עם מק"ט `-9999`. אם ריבית תשלומים
והנחה ברמת הזמנה לא הפכו לשורות — הפער ייפול בדיוק על ההזמנות שבהן השדות האלה לא אפסיים,
ו-15.49% הוא שיעור סביר מאוד להזמנות בתשלומים.

`dry-run` בודק את זה ישירות: הוא סופר כמה מההזמנות החורגות מוסברות ע"י
`interest - discount`, ומדפיס דוגמאות למה שלא מוסבר. אם הרוב מוסבר — זה תיקון קטן במסווג
(להוסיף שורת fee לריבית ולהנחה) ולא בעיית דאטה.

**שווה להריץ `dry-run` לפני הייבוא המלא.** זה הבדל בין לייבא 133k הזמנות נכונות לבין
לגלות אחרי המעשה ש-20k מהן לא מסתדרות.

## הערכת זמן

| שלב | זמן |
|---|---|
| `inspect` + התאמת field map | 15–30 דק' |
| `dry-run` על 133k (פרסור בלבד) | 5–10 דק' ריצה |
| בירור פערי הסכומים + תיקון מסווג | 1–2 שעות |
| סמפל 500 + אימות עין | 30 דק' |
| ייבוא 75,186 לקוחות | 30–50 דק' |
| ייבוא 133,194 הזמנות | 1.5–3 שעות |
| ולידציה: השוואת ספירות וסכומים למקור | 1 שעה |
| `relink` אחרי הקטלוג | 15 דק' |

**סה"כ: יום עבודה ממוקד — בערך 6–9 שעות**, מתוכן **~2–4 שעות ריצת מכונה לא מפוקחת**
(להריץ ב-screen).

הערכת קצב ההזמנות מבוססת על WooCommerce CRUD עם hooks מנוטרלים — סדר גודל של
15–40 הזמנות/שנייה. הבחירה ב-CRUD ולא ב-INSERT ישיר ל-HPOS היא מכוונת: סכמת HPOS
משתנה בין גרסאות Woo, וכתיבה ישירה בלי לראות את השרת היא סיכון מיותר. אם הקצב בפועל
יתברר כאיטי מדי אחרי הסמפל — אפשר להחליף את `create_order()` לכתיבה מרובת-שורות.

## מה לא כלול

סליקה, חשבוניות ומסמכי מס לא מיובאים (לפי התוכנית). ההזמנות נכנסות בסטטוס `completed`
עם התאריכים והסכומים המקוריים.
